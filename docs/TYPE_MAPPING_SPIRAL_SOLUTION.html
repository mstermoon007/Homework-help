题型·知识点映射与能力螺旋上升 · 总体解决方案

四层架构对齐版 ｜ 解决「知识点与题型对应不准确」与「题型模块限制『知识点驱动习题生成』能力螺旋上升」 ｜ 依据项目权威四层架构（architecture/layers.json） ｜ 2026-09-04
一句话结论：问题的本质是「层职责错位」——题型决策（选择、过滤、题量分配）散落在 UI 层、题型枚举在知识点库层内部多套割裂、校验无语义门槛。解决方案按四层架构收敛：数据在知识点库、决策在大服务层、执行在生成层、展示在 UI 层；题型枚举收敛为知识点库单一事实源（SSOT），过滤与分配决策上收大服务层、UI 只发指令收结果，生成层能力声明为唯一可信依据，配一致性门禁分 6 阶段落地，最终解锁能力螺旋上升。

零、项目四层架构（权威定义）

本项目为「物理稳定 + 逻辑清单」架构：文件留驻 shared/，逻辑归属以 architecture/layers.json 为唯一权威分类（npm run verify:layers 校验覆盖率，未分类即 FAIL）。

UI 层
页面壳 / 交互 / 渲染呈现入口。典型：*.html、feedback/、knowledge/*.html、sw.js。
红线：不决策题目结构；不直连生成引擎算法（唯一入口 PracticeBridge.start，check-ui-boundary.js 门禁锚定）；不得直调 Strategy/Generator/Plugin.generate。
大服务层
信息传递 / 项目控制 / 外围样式 / 打印等外围控制；除 UI/生成/知识外全归此层。典型：practice-bridge.js（唯一生成入口）、strategy/**、validator/**、capability-*.js、learner/**、module-catalog.js、*.css。
红线：只做信息传递/控制/编排，不侵入 Frozen Core 生成算法。
生成层
题目生成核心引擎：题面/答案算法生成、语义归一、渲染(HTML/SVG)输出。典型：generation-engine.js、practice-session.js、generator/**、presentation/**、svg-*.js、plugins/**。
红线：Frozen Core，仅授权 Bug Fix(GEN)；只接受指令生成题目，不承载 UI 交互决策。
知识点库
基层数据核心：唯一数据来源、schema、规范映射。典型：knowledge-*.js、knowledge-ontology*.js、schemas/knowledge-point.schema.js、question-type-registry.js、ontology-*-map.js。
红线：不生成题面、不参与 UI 决策。

注：layers.json 中 shared/schemas/knowledge-point.schema.js 同时在「GENERATION/SEMANTIC」与「KNOWLEDGE」两处登记，属既有双归属待治理点，本方案阶段 0 一并收敛。

一、问题定位：层视角重述两条病根

1.1 病根 A：知识点与题型对应不准确 = 知识点库内题型枚举割裂 + UI 越层决策

  • 知识点库层内部枚举割裂：「题型」在知识点库内出现两套定义——schemas/knowledge-point.schema.js 的 KNOWN_QUESTION_TYPES（7 类，含 operate）与 question-type-registry.js 的 TYPES（9 类，含 oral/geometry/recognize），互不一致且无一致性门禁；normalizer 别名（TYPE_ALIAS）把 oral/recognize/picture→operate，registry 再 operate→oral，两跳漂移。
  • 知识库数据依赖启发式兜底：全库 574 知识点中 494 个（86%）的 applicable_question_types 用非 canonical 值；40 个题型值靠关键字启发式（array-closed→geometry 数阵图归几何、pie-chart→calc 扇形统计图归计算等），能力决策 614/614 假性全 ALLOW，题型区分度崩塌。
  • UI 层越层承担决策：practice.html 用 QT_STD_MODULES 静态表做题型→模块过滤（kpVisibleInQT）、自实现 kpRatio 最大剩余法分配——这些题目结构决策应在大服务层（strategy 的 question-type-allocation.js 已存在），UI 层本应只展示。越层使「页面过滤」与「生成层能力」脱节（QT_STD_MODULES.calc=[M2,M3] 不含 M1，深链 ?qt=calc 过滤掉口算知识点，而生成层能力层明确支持）。
  • 校验无语义门槛：M1-R06 只统计不设 FAIL；无「题型合法性 / 三向一致性」门禁。

1.2 病根 B：题型模块限制螺旋上升 = 模块被当决策层 + 决策未收敛

  • 模块（大服务层 module-catalog）被当作生成能力决策层：出题入口 = 模块多选，知识点被锁死在模块内，无法跨模块按能力组合（「口算题型 × 数认识知识点」不可达）。
  • 模块↔题型↔知识点三向关系无单一事实源：页面用 QT_STD_MODULES（题型→模块）、知识库用 moduleId（知识点→模块）、生成层用归一化 capability（知识点→题型）——三张表手工维护、互不一致。
  • 螺旋提升建立在失真的题型声明上：题型声明被启发式抹平 → spiral-strategy 变体维度 / 前置门 / 难度自适应失真 → 能力无法真正螺旋上升。地基不牢，上层策略再精巧也失真。
核心洞察：两条病根同源——「决策」没有收敛到它该在的层（大服务层），而散落在 UI 层与知识点库的旁路里。因此方案主线是「层职责复位」：题型枚举收敛到知识点库 SSOT、过滤/分配/能力决策上收大服务层、生成层能力为唯一可信依据、UI 只展示。

二、目标与设计原则（含层原则）

原则含义归属层
层职责复位数据在知识点库、决策在大服务层、执行在生成层、展示在 UI 层；UI 不决策题目结构、知识库不参与 UI 决策。全局
题型 SSOT题型元数据唯一权威定义（question-type-registry，知识库层），schema 与页面引用之，消除 operate/oral 割裂与双归属。知识点库
显式映射优先知识库题型值必须 canonical / 显式别名，启发式归零并由门禁禁止。知识点库
能力驱动过滤/分配/可见性决策由大服务层基于知识点归一化能力给出，UI 只发指令收结果；模块回归展示分组。大服务层
门禁护航每阶段新增/收紧校验并纳入 CI；触碰 Frozen Core 前 GEN 授权 + 基线快照。治理(dev)
分阶段可回滚每阶段独立 commit、可单步 revert；先试点（G1）后铺开。全局

三、目标架构：四层内的一条主链

目标态：UI 只发指令 → 大服务层规划（题型/过滤/分配/螺旋）→ 生成层执行 → 回 UI 展示，知识点库供数，模块只做展示分组。

UI 层
发出「科目+年级+题型+题量」指令（PracticeBridge.start）；展示结果；不再持有题型过滤表、不再做能力判断、不再自实现分配。
大服务层
接收指令 → 读知识点库能力 → 规划：题型可见性/题量分配（question-type-allocation）/难度/螺旋（strategy/**）→ 生成请求（含 kpAllocation）→ 派发到生成层；批改分发（practice-bridge）。
生成层
按请求（kp + questionType + 题量）经 generator/** 生成题面/答案并渲染输出；只执行指令，不决策选哪题、出几题。
知识点库
提供知识点数据（含 canonical 题型声明、五类本体字段、考试地位元数据）；题型注册表为 SSOT；不生成题面。
