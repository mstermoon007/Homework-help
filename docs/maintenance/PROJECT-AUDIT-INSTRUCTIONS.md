# 小学练习本｜综合审计与持续维护指令

## 一、项目目标

对小学练习本项目进行持续、全面、可验证的审计与维护。

项目地址：[https://home.modouyu.top/](https://home.modouyu.top/)

项目定位：纯前端小学练习工具，逐步完善数学练习产品，后续扩展其他学科。

核心功能：首页、年级与科目选择、题型选择、题目生成、在线练习、答案批改、预览、打印。

核心目标：

1. 保证题目生成、答案计算、练习批改和打印结果正确。
2. 保证架构清晰、模块职责明确、核心链路唯一。
3. 识别并实施有实际收益的架构、链路和模块优化。
4. 统一 JavaScript 代码风格与语义，降低持续开发成本。
5. 清理无效代码、重复逻辑、废弃文件和无效依赖。
6. 保证本地、Git、构建产物与服务器之间的版本一致。
7. 建立可持续执行的审计、修复、测试和发布流程。

## 二、必须遵守的开发约束

1. 先读取开发历史、现有架构规范、任务清单和验收报告。
2. 以当前真实代码和验证结果为准，不直接沿用历史 PASS 结论。
3. 直接修改原文件，不复制文件建立第二套实现。
4. 解决根因，不使用新增开关、兼容层、重复判断掩盖问题。
5. 不重建已完成且仍然有效的体系，不重复执行已完成任务。
6. 不修改与当前问题无关的代码。
7. 保持现有首页样式、按钮、链接、交互和打印体验。
8. 不擅自修改已冻结的知识源、难度公式、随机机制及其他明确冻结的核心实现。
9. 不引入登录、数据库、客户信息存储、广告、第三方运行时或 AI Agent。
10. 不擅自改变既定架构分层、数据契约及核心调用链。
11. 未经验证不得标记 PASS，不得虚构测试、构建或线上检查结果。
12. 不覆盖用户未提交的修改，不擅自清除 Git 未跟踪文件。
13. 未经评估不得进行大规模重构、批量删除或生产目录清理。
14. 每个问题只保留一个权威实现；确认无用后直接清理重复实现。
15. 优化必须有明确收益、实施范围和回归验证，不以代码行数减少作为唯一目标。

## 三、阶段一：开发历史与当前状态审计

### 任务

1. 阅读现有开发日志、阶段任务书、架构规范、验收报告及遗留问题。
2. 检查 Git 分支、提交记录、工作区状态、未跟踪文件和未提交修改。
3. 核对历史已完成事项、当前实际实现及尚未完成事项。
4. 检查本地源码、Git 提交、构建产物和线上版本是否一致。
5. 识别重复任务、过期文档、冲突规范及失效验收结论。
6. 建立唯一的当前审计清单，更新原有记录，不创建重复台账。

### 交付

- 当前版本与提交基线。
- 已完成事项及复核结果。
- 真实问题与遗留任务。
- 需要保护的修改及冻结范围。

## 四、阶段二：架构、数据与核心链路审计

### 任务

1. 检查 KBL 知识源、派生数据、知识点映射及生成能力的一致性。
2. 检查 POL、Strategy、Generator、Validator、Presentation 的职责边界。
3. 检查 PracticeSession、GenerationAPI、PracticeOrchestrator、StrategyEngine、PresentationEngine、BatchValidator、SemanticQuestion 及题目渲染之间的实际调用关系。
4. 检查题型、题量、难度、知识点的唯一权威来源。
5. 检查标准答案、用户答案、批改结果和展示结果是否保持一致。
6. 检查重复入口、重复数据源、循环依赖、隐式全局变量和职责越界。
7. 检查错误处理、返回结构、数据契约和异常传播是否统一。
8. 检查模块之间是否存在重复转换、重复校验、无效传递或不必要的中间层。
9. 检查历史兼容代码、旧接口和遗留引用是否仍然必要。
10. 不因历史文档中的调用链描述而认定当前实现正确，必须核对真实代码。

### 交付

- 实际架构与调用链问题。
- 数据权威性和职责边界问题。
- 最小修复方案及回归结果。

## 五、阶段三：架构、链路与模块优化空间专项评估

### 目标

除排查缺陷外，主动判断项目现有架构、业务链路和模块是否仍有优化空间，并识别最值得实施的优化事项。

### A. 架构优化

1. 是否存在过度分层、无效抽象或不必要的架构复杂度。
2. 是否存在多个模块共同承担同一职责。
3. 是否存在一个模块承担过多职责、修改影响范围过大的问题。
4. 是否存在重复注册、重复配置、重复路由或重复数据定义。
5. 是否存在不必要的兼容层、适配层、包装层和中间转发。
6. 是否存在模块依赖混乱、循环依赖或依赖方向错误。
7. 是否可以在保持原有架构原则的前提下减少维护成本。

### B. 核心链路优化

1. 是否存在重复生成、重复校验、重复计算或重复渲染。
2. 是否存在数据在多个模块之间反复转换。
3. 是否存在调用顺序不合理、重复调用或不必要的等待。
4. 是否存在异常处理分散、失败后无法恢复或错误信息丢失。
5. 是否存在题目数量、题型、难度和答案在链路中发生偏移。
6. 是否存在练习、批改、预览、打印和备用路径之间的语义不一致。
7. 是否可以减少链路复杂度，同时保持唯一权威来源和完整验证。

### C. 模块优化

1. 是否存在过大、过度耦合或难以独立测试的模块。
2. 是否存在功能重复、代码重复或相同规则的多份实现。
3. 是否存在仅转发调用、没有实际业务价值的模块。
4. 是否存在不必要的文件拆分或不必要的文件合并。
5. 是否存在模块接口不稳定、参数含义不清、返回结构不一致。
6. 是否存在过度依赖全局状态、隐式副作用或不明确的执行顺序。
7. 是否存在可以通过小范围修改显著降低维护成本的模块。

### D. 性能与维护成本优化

1. 检查首屏加载、脚本体积、资源请求和重复加载。
2. 检查不必要的计算、重复渲染、事件监听及内存占用。
3. 检查大文件、重复依赖、无效代码和过度复杂的控制逻辑。
4. 检查测试难度、故障定位成本及修改引发回归的范围。
5. 判断优化是否具有实际收益，避免无数据依据的性能重构。

### E. 优化实施规则

1. 将优化机会分为：
   - O0：直接影响正确性、安全性或生产稳定性的结构问题。
   - O1：显著降低核心链路复杂度、重复实现或维护风险的问题。
   - O2：具有明确收益的性能、模块边界和代码维护优化。
   - O3：收益较小、风险较高或暂时没有必要实施的优化。
2. 每项优化必须明确当前问题、根本原因、目标状态、涉及文件、预期收益和验证方式。
3. 优先采用原文件最小修改，避免无必要的大规模重构。
4. 不为了追求更少文件、更少代码或更漂亮的目录结构而破坏职责边界。
5. 不得建立第二套架构、第二条业务链路或第二套规则。
6. 优先实施收益明确、影响范围小、容易回归验证的优化。
7. 对高风险或收益不明确的优化，先记录，不直接实施。
8. 涉及冻结模块、架构原则或核心数据契约时，必须先获得明确授权。
9. 优化完成后必须通过针对性测试及相关回归测试。
10. 若当前架构已经合理，应明确记录“未发现值得实施的结构性优化”，不得为完成任务强行重构。

### 交付

- 架构优化清单。
- 核心链路优化清单。
- 模块优化清单。
- 性能与维护成本优化清单。
- 每项优化的优先级、涉及文件、预期收益、风险和验证结果。
- 已实施、暂缓及不建议实施的事项。

4. 检查答案计算、单位、分数、小数、运算符号和边界值。
5. 检查重复题、无效题、超纲题及题干与答案不一致。

7. 检查题目、标准答案、批改规则和展示内容的一致性。
8. 使用可复现测试验证关键问题。
9. 不擅自修改冻结的知识源、难度公式和随机机制。

### 交付

- 分年级、分题型测试结果。
- 失败案例及根因。

7. 检查页面刷新、返回操作及不同屏幕尺寸下的表现。

### 交付

## 八、阶段六：JavaScript 代码质量审计

### 任务

1. 检查命名、参数、返回结构、异常处理和注释是否统一。
2. 检查重复函数、重复规则、死代码和无效依赖。
3. 检查模块职责、全局变量、事件监听和隐式副作用。
4. 检查脚本加载顺序、重复打包和资源引用。

6. 检查移动端布局、键盘操作、语义标签和基本可访问性。
7. 优先修复真实缺陷和影响维护的语义歧义。
8. 仅在收益明确、风险可控时拆分或合并模块。

### 交付

- 重复代码及废弃文件清理记录。

## 九、阶段七：安全、隐私与离线审计

### 任务

1. 检查外部请求、追踪脚本、第三方依赖及数据上报。
2. 验证题目和作答数据不会被上传至业务服务器或第三方。
3. 检查不安全 DOM 操作、输入处理和 XSS 风险。
4. 检查 HTTPS、静态资源访问和安全响应头。
5. 检查 Service Worker 更新、离线访问、缓存失效和版本切换。
6. 检查公开文件及发布产物是否包含敏感信息。
7. 保持纯前端运行模式，不新增用户信息存储。

### 交付

- 安全检查结果。
- 隐私链路验证。
- 离线与缓存测试结果。

## 十、阶段八：生产服务器审计

4. 区分正常浏览器访问、爬虫、自动化请求和异常流量。
5. 检查线上旧文件、无效资源、缓存和版本不一致。
6. 验证服务器只保留生产运行文件。
7. 不将源码、测试、开发工具及审计文档直接部署到服务器。
8. 不开放公网统计页面，不持久化客户练习数据。
9. 删除线上旧文件前必须确认目录、删除范围及回滚依据。

### 交付

- 服务器状态与线上版本检查。
- 资源错误及异常访问记录。

## 十一、阶段九：自动化测试与发布验收

### 任务

1. 执行静态检查、单元测试、集成测试和端到端测试。
2. 执行核心生成、答案、批改、打印及知识库回归测试。
3. 执行完整构建并检查所有运行资源。
4. 检查 Git 工作区，保护未提交修改，确认本次提交范围。
5. 使用唯一的构建流程生成 dist。
6. 检查 dist 不包含测试文件、开发工具、审计文档和不必要源码。
7. 使用既定部署流程发布，不随意上传整个项目目录。
8. 发布后验证首页、练习主链路、批改、打印、离线缓存和错误日志。
9. 记录版本、Commit、构建结果、测试结果及回滚方式。
10. 发布失败时优先回滚至已验证版本，不在生产环境临时拼凑文件。

### 交付

- 构建结果。
- 自动化测试与回归结果。
- 发布验收单。
- 版本及回滚记录。

## 十二、问题优先级与验收规则

### 问题优先级

P0：核心出题、答案正确性、安全或生产运行存在严重问题。

P1：主要业务链路失败、数据契约不一致、核心功能明显退化。

P2：模块重复、代码质量、性能或维护成本问题，且收益明确。

P3：低风险、低收益或暂时不影响运行的改进事项。

### 状态规则

PASS：已执行验证并通过。

FAIL：存在可复现问题，尚未通过验证。

BLOCKED：因权限、环境或依赖缺失无法继续。

NOT TESTED：尚未执行验证。

所有问题必须保留复现步骤。所有修复必须有测试结果。未完成事项不得标记 PASS。

## 十四、执行方式

1. 先完成阶段一，确认当前真实状态。
2. 再执行阶段二和阶段三，完成架构检查及优化空间评估。
3. 按优先级依次执行阶段四至阶段八。
4. 先修复高优先级缺陷，再实施收益明确的结构优化。
5. 完成阶段九的完整回归与发布验收。
6. 每个阶段结束后更新现有开发日志和任务状态。
7. 未完成当前阶段验收，不进入下一阶段。
8. 每次维护优先处理新增问题、回归问题和高收益优化，不重复执行无变化的历史任务。
9. 如需修改冻结模块或改变既定架构，先提交变更请求，等待明确授权。

最终原则：

**先查真实状态，再修根因；先保证正确，再优化架构；先减少重复，再提高性能；先完整验证，再发布上线。**

项目持续进步，但不为审计而审计，不为重构而重构，不建立第二套架构，不让代码治理成本超过实际产品收益。
